# Plasmaの開発をローカル反映まで完了する

ユーザーの継続指示として、Plasmaの改善・修正依頼は「ゴール設定 → 実装 → 検証 → ローカルプラグイン更新 → 再起動または画面の開き直しの案内」を一つの作業単位とする。コード変更やビルド成功だけで完了にしない。ユーザーが今回の範囲を限定した場合はその指示を優先する。

## ゴールと作業範囲

- 改善・修正の実装を依頼されたら、公開された `get_goal` で状態を確認し、同じ目的のゴールがなければ `create_goal` で設定する。このゴール設定は本スキルを作成したユーザーの明示的な継続指示に基づく。予算は指定がある場合だけ付ける。
- ゴールの完了条件に、要求された挙動、検証、ローカルプラグインへの更新、必要なユーザー操作の案内を含める。会話途中の追加要求も作業範囲へ反映する。
- 無関係な未完了ゴールで登録できない場合、勝手に完了扱い・削除しない。状況を説明し、ユーザーによる整理を依頼する。ゴール管理には公開ツールだけを使い、その状態遷移の条件に従う。
- この会話と現在のチェックアウトで作業する。別セッション・worktreeの作成、コミット・push・公開はこのスキルによって許可されない。
- 相談・読み取り調査では勝手に実装へ進まない。ドキュメントやスキルのみの変更で実行物に影響しない場合は、不要なランタイム更新をせず、反映不要である理由を報告する。

## 実装と検証

1. `git status` と既存差分、適用される `AGENTS.md`、`package.json` を読み、未コミットの作業を保ったまま対象機能の構成を確認する。依存管理はリポジトリ指定のpnpmを使う。
2. 既存の設計に沿って実装する。実装後は「削れないか」を検討する簡素化工程を入れ、その後にセルフレビューする。
3. 変更に必要なテストとチェックを完了する。現在の基本コマンドは `pnpm check`、`pnpm typecheck`、`pnpm test`、`pnpm build`。失敗を隠さず、再試行でしか通らない場合は不安定さを記録する。
4. UI変更は最新ビルドを実画面で操作し、要求された見た目と挙動を確認する。ファイル操作・Git・ターミナルの検証は使い捨てのプロジェクトを用い、ユーザーの作業ファイルをテスト材料にしない。HTTPプレビューでの確認と、インストール済みMCPプラグインでの確認を区別する。

## ローカルプラグインへの反映

手順の根拠はリポジトリルートの `docs/local-distribution.md`、`scripts/prepare-local-plugin.ts`、`server/mcp.ts`。固定のユーザー名・絶対パス・バージョンをこのスキルへ埋め込まず、実行時の登録先とコードを確認する。

1. `codex plugin marketplace list` と `codex plugin list --marketplace workbench-local --json` で現在の登録元・インストール状態を確認する。CLIが変わっていれば `codex plugin --help` など公開ヘルプを読む。
2. 最終変更を含む `pnpm build` を完了し、`pnpm run setup:plugin` でローカル定義を生成する。これは `.shinaps/work/local-marketplace` に定義とアイコンを生成する処理であり、インストール済みキャッシュの更新を保証する処理ではない。
3. 生成された `.mcp.json` の実行ファイル・引数・cwdと、実際にインストール済みのプラグインが参照する設定を照合する。既存IDは `typescript-workbench@workbench-local`、表示名は Plasma。重複インストールや無断のID変更をしない。
4. このチェックアウトを直接参照している場合、最新の `dist/index.html` とサーバーソースが参照先にあることを確認する。コピーされた配布物や古い定義を参照している場合は、現在利用できる公式のローカル更新手順で反映し、登録先を読み戻す。単にアーカイブを作っただけでは更新完了にしない。キャッシュ・レジストリの内部ファイルを手で書き換えて更新を装わない。
5. 更新手順が削除や別の登録先への移行を必要とする場合は、既存設定を保てる方法を先に検討する。更新を完了できない場合は未完了箇所と必要な操作を説明し、ゴールを完了にしない。

## ユーザーへの引き渡しと完了

- フロントエンドのみの変更で、新しいリソースを取得すれば反映されることを確認できた場合は「Plasmaの画面を閉じて開き直してください」と案内する。
- MCPサーバー・プロトコル・起動設定・依存関係を変更した場合や、古いサーバーが残っている場合は「Codexを再起動してPlasmaを開き直してください」と案内する。古いサーバーと新しいUIの組み合わせで未対応opエラーになるため、画面の開き直しだけで十分とは言わない。
- ユーザーのCodexや稼働中ターミナルを勝手に終了しない。再起動はユーザーに依頼する。
- 最終報告には、変更の要点、実際に通った検証、ローカル反映の確認結果、ユーザーに必要な操作を短く書く。「更新済み・再起動待ち」と「再起動後の実機動作も確認済み」を混同しない。
- 実装・必要な検証・ローカル更新が済み、残る作業が案内済みの再起動／開き直しだけならゴールを完了できる。受入条件に再起動後の実機検証を含めた場合は、その確認まで完了にしない。
