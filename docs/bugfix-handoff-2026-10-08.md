# Plasma 不具合修正・検証の引き渡し

作成日: 2026-10-08。対象: 現在の Plasma チェックアウト。

## 目的と担当範囲

Claude のレビュー報告と Codex の差分エディタレビューを統合し、妥当性の確認、修正、回帰検証、ローカルプラグイン更新まで進めるための手順書。
本書の作成時点では製品コードの修正、UIでの追加再現確認は行っていない。実機検証の手順は下記に定義した。

実装担当は最初に `AGENTS.md`、`.agents/skills/plasma-development/SKILL.md` と現在の差分を確認する。大量の未コミット・未追跡の既存作業があるため、リセット、既存差分の巻き戻し、全体への自動整形をしない。コミット・push・別 worktree・別セッションへの委託は本書によって許可されない。

本書のファイル位置は探索の入口であり、報告時の行番号は固定しない。各項目は現行コードで再確認する。実装担当が完了した項目を後から別担当が同時修正しない。

## 根拠と完了の扱い

- **C**: ユーザーが共有した Claude 報告ではコード照合済み。Codex が全件を独立検証したという意味ではない。
- **R**: Codex がコード上の経路を確認。ただし実機で同じ例外を再現したとは限らない。
- **H**: 仮説。再現・影響・意図した仕様の確認を経て、修正対象か判断する。
- **M**: 元の報告の詳細不足。調査対象として残し、根拠を補うまで確定扱いしない。

「怪しいコードを直せば元の不具合も直ったはず」とは扱わない。成立している周辺不具合は先に直してよいが、元の症状には別の検証結果を付ける。
各項目は `未確認 → 確認済み → 修正済み → 検証済み` を記録し、非該当なら理由と根拠を残す。再現できない項目を黙って完了にしない。

## 修正の順序

1. 現行状態と検証環境を記録。特に `activeElement` のスタックと処理段階を取得できるようにする。
2. Git・保存のデータ整合性を修正（G2、G5、S2、および詳細補完後のM1/M2）。既存ファイル・index・未選択変更を壊さないことを最優先する。
3. 操作不能や永続的な停止を修正（G1、G4、E3、E4、D1〜D3、T1）。
4. ファイル復元、URI、診断、フォーカス、UI状態を修正（E1、E2、E5〜E7、U1/U2、確認されたH項目）。
5. サーバー寿命・キュー・性能を調整（S1、S3〜S5、T2/T3）。性能改善は測定と責務整理を先に行う。
6. 契約・ドキュメント・検証基盤を整え、統合回帰とローカル反映を行う。

順序は被害と依存関係に基づく。変更を一括投入せず、同じ原因の小さな単位ごとに再現、修正、簡素化、セルフレビュー、検証を終える。

#### D0の調査手順

1. 修正前の版、ビルド、Monacoバージョン、HTTP/MCPホスト、操作順を記録する。古いMCPサーバーと新UIの組合せを切り分ける。
2. `open → 旧モデル切離し → 表示切替/layout → editor.create → updateOptions → setModel → bind/restore/focus` のどこで失敗するか、元Errorのstackと世代番号・エディタ種別で追う。ソース本文・認証情報はログに含めない。
3. 使い捨てリポジトリで、追加・変更・削除・名前変更・画像・通常ファイルを切り替える。自動再取得や非同期応答が重なる状態、タブ閉じ・開き直しも確認する。
4. スタックがMonaco内部なら呼出し元と渡したDOM/document/windowの状態を調べる。証拠なくMonacoのfork・依存更新・内部コードへのガードを追加しない。
5. D1〜D3はモデル設定・差分計算の失敗を注入して別途検証できる。このテスト成功はD0再現・解消の証明ではない。
6. D0が再現しない場合は「周辺不具合修正済み／元の例外は未再現」と報告し、診断情報の取得方法を残す。

## 実装と検証のルール

- 修正前に最小の再現を作る。データ整合性・非同期・失敗復旧は回帰テストを残す。CSSやDOM構造をなぞるだけのテストは増やさない。
- 部分コミットではHEAD・実index・worktree・未選択内容の前後を比較する。Git属性やmergeを扱う試験は実プロジェクトで行わない。
- 失敗注入は本番経路への恒久的な特例追加より、既存の依存境界かテスト専用fixtureを使う。
- 複雑な互換層やワークアラウンドが必要になる場合は、単純な設計変更・対応範囲縮小をユーザーへ提案してから進める。
- 実装後に「削れないか」を確認する簡素化工程を入れ、その後セルフレビューする。
- 基本検証は `pnpm check`、`pnpm typecheck`、`pnpm test`、`pnpm build`。既存失敗と今回の失敗を区別し、通るまで意味なく再試行しない。
- 統合UIではproject開閉、ネスト文書復元、差分切替、左右の自然な行配置と追従、中央幅変更、部分選択、保存・commit、terminal、設定draftを確認する。

## ローカル反映と完了報告

実装時は `.agents/skills/plasma-development/SKILL.md` と `docs/local-distribution.md` に従う。
最終ビルド後の `pnpm run setup:plugin` だけでインストール済み更新を断定せず、登録済みプラグインの参照先と生成物を照合する。内部キャッシュを手で編集しない。

サーバー・プロトコル・依存関係の変更を含むため、ユーザーには原則「Codexを再起動しPlasmaを開き直す」よう案内する。稼働中のCodexやterminalを勝手に終了しない。

最終報告は次を含める。

1. 台帳IDごとの修正済み／非該当／未確定／仕様確認待ちと根拠。
2. 実際に通った検証、HTTPとMCPのUI確認範囲。
3. D0の元症状の再現・解消確認と、D1〜D3の復旧検証を別記。
